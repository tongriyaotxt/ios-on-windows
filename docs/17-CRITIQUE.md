# 17 · 问题分析（自审）

> 这份文档是给自己挑刺的。写它的目的不是自我否定，而是让接手的人知道**哪里会先坏**。
> 分级：**P0** 会让「能跑」这个结论失效；**P1** 会在特定条件下坏；**P2** 维护负担；**P3** 体验问题。

---

## 1. 结构性问题

| # | 问题 | 级别 | 说明 |
|---|---|---|---|
| 1 | **dylib + constructor 是绕行方案** | **P0** | 可执行体只做 `LC_LOAD_DYLIB`，界面在 dylib 的 `__attribute__((constructor))` 里起。这是为了绕开 zig 链接器在 `MH_EXECUTE` + 外部符号上的溢出。dyld 保证 initializer 在 `main` 之前跑，但**没有任何文档保证 UIKit 允许在 initializer 里接管 run loop**。模拟器里跑通了（`docs/11`），真机仍是未知 |
| 2 | **不是构建系统，是编译命令** | P1 | `Build-IosAppNative.ps1` 只接受**一个** `.m` 文件。没有头文件图、没有多目标、没有增量。真实 App 一上规模就得重写这一层 |
| 3 | **Mach-O 解析重复 5 份** | P2 | `machogen` / `codesign_lite` / `verify-ipa` / `audit-device` / `sim-ios` 各有一套 load command 遍历。改一处忘四处 → 审计和实际行为不一致（这类 bug 最难查，因为"审计说没问题"） |
| 4 | **`.tbd` 靠手写维护** | P1 | 新用一个系统 API → **编译通过、运行崩**（`Symbol not found`）。没有任何自动化把「代码里调了什么」和「存根里有什么」对上 |
| 5 | **PowerShell 5.1 的 BOM 陷阱** | P2 | 无 BOM 的 UTF-8 脚本会被按 GBK 读，中文注释会吞掉下一行。本次开发中踩了 **6 次**，每次都表现为"莫名其妙的语法错误"。只能靠约定（`docs/12`）和 CI 检查 |

## 2. 正确性风险

| # | 问题 | 级别 | 现状 |
|---|---|---|---|
| 6 | **签名页大小 4KB 未在真机确认** | **P0** | 4KB 是 iOS 上的常见值，但没法在这里验证。已做成开关（`CODESIGN_PAGE_SIZE=14` = 16KB），失败可以一次实验定位 |
| 7 | **没有嵌套代码封印** | P1 | `codesign` 会把 `Frameworks/*` 的哈希记进父签名；我们只做了资源信封（`CodeResources`）。iOS 版本较严时可能报 `code object is not signed at all` |
| 8 | **确定性只对 ad-hoc 成立** | P2 | 真证书签名时 CMS 里带 signing time，`-Deterministic` 失效。要真可复现得固定 CMS 时间（Apple 未必接受） |
| 9 | **模拟器是模型，不是实现** | P1 | 假 UIKit 只覆盖 ~20 个 selector。它能证明控制流/ABI/数据流，**不能**证明布局、生命周期、渲染。把它的 PASS 当"能跑"是误读 |
| 10 | **entitlements 只用合成 profile 验过** | P1 | 用自签证书 + 自造描述文件跑通（审计 FATAL=0），但没有一份 Apple 真描述文件参与过 |

## 3. 安全问题

| # | 问题 | 级别 | 说明 |
|---|---|---|---|
| 11 | **`refresh.json` 明文存 p12 密码** | P1 | 计划任务要用它。文件在 `.gitignore` 里，但**落盘明文**。应该用 DPAPI（`[ProtectedData]::Protect`）或 Windows 凭据管理器 |
| 12 | **`.env` 明文** | P1 | 同上。ASC 的 `.p8` 本身是私钥文件，至少它是文件权限保护；`.env` 里的 issuer/key id 不算敏感，但习惯不好 |
| 13 | **cpio 路径穿越** | P1（**已修**） | `xip-extract.py` 原本把 `../../x` 直接拼到输出目录 → 可写出目录外。已加 `..`/绝对路径/盘符检查，并补了正反用例。这是本次自审里唯一真的可利用项 |
| 14 | **zip/ipa 无大小上限** | P2 | `verify-ipa` / `sim-ios` 读 ipa 时不限制条目大小，恶意包可以做成 zip bomb 打爆内存。本地工具，风险低，但容易被当 issue 提 |
| 15 | **模拟器映射任意地址** | P3 | Unicorn 里不做边界检查，跑恶意二进制可能让 Python 崩。仅本地运行，可接受 |

## 4. 法律与合规

| # | 问题 | 级别 | 说明 |
|---|---|---|---|
| 16 | **`xip-extract.py` 的用途边界** | P2 | 工具本身中立（只解包你给的文件）。但用抽出来的 SDK 编 App，受 Apple 开发者协议约束。README/LICENSE 已写明"仓库不含 Apple SDK 文件" |
| 17 | **TrollStore 路径涉及绕过代码签名** | **P1（发布风险）** | CoreTrust 漏洞利用在部分司法辖区可能触及反规避条款。目前的处理：**不放在 README 主推路径**，只写在 `docs/16` 的安装选项里，并注明是用户自己的选择 |
| 18 | 仓库不含 Apple 二进制 | ✅ | `sdk/iPhoneOS-shim` 是手写符号名；`LICENSE` 里已声明 |

## 5. 工程与维护

| # | 问题 | 级别 | 说明 |
|---|---|---|---|
| 19 | **zig 版本强耦合** | P1 | `ziglang==0.17.1`。升级可能改变 Mach-O 输出或修掉那个链接器 bug（修掉反而好，但要重写 dylib 方案）。`docs/12` 已把"升级必须跑全链路"写成规矩 |
| 20 | **CI 从未在真 GitHub 上跑过** | P1 | `ci.yml` 在本地用同样命令验证过，但没有一次真实 Actions 运行记录。第一次跑大概率要修 `pwsh`/`openssl` 的平台差异 |
| 21 | **文档中英混排** | P2 | README 英文、`docs/` 全中文。对外国贡献者是门槛；对你是效率。短期取舍，长期要拆 |
| 22 | **Python 工具没有包结构** | P2 | 12 个脚本靠 `sys.path` 互相引用，没有 `pyproject` 打包。做 `pip install` 分发要先重构 |
| 23 | **缺 issue/PR 模板** | P3 | 已有 `CONTRIBUTING.md` 里的设备报告模板，可以再固化成 `.github/ISSUE_TEMPLATE` |

## 6. 风险矩阵（概率 × 影响）

```
影响大
  │  ①constructor 起 UI 不被允许（P0，概率中）
  │  ②页大小 4KB 被拒（P0，概率低）
  │  ③嵌套代码封印缺失（P1，概率中）
  │  ④.tbd 少符号导致运行崩（P1，概率高但只在加新 API 时）
  │  ⑤zig 升级破坏出品（P1，概率中）
  │  ⑥CI 首跑失败（P1，概率高，但一小时能修）
  └────────────────────────────── 概率高
```

前两项一旦发生，「Windows 上能出可运行 App」这个结论就要退回「Windows 上能出结构合法的包」。

## 7. 如果只修三件事

| 优先级 | 做什么 | 为什么 | 成本 |
|---|---|---|---|
| **1** | **真机跑一次**（TrollStore 或免费账号） | 一次实验就能把 ① 和 ② 从「未知」变成「已知」，这是整份文档里最重要的不确定性 | 10 分钟 + 一台设备 |
| **2** | **合并 Mach-O 解析到 `tools/macho.py`** | 五个副本意味着「审计通过但实际不一致」的隐患；这类 bug 会让人不再信任审计 | 半天 |
| **3** | **`.tbd` 符号自动发现** | 把「运行期崩溃」提前到「构建期报错」，否则每加一个 API 都是一次真机赌博 | 一天 |

其余（嵌套封印、CMS 确定性、zip 上限、issue 模板）都是加分项，不影响结论成立。

---

## 8. 一句话

**这个项目最大的问题不是"哪里写错了"，而是"有一个关键假设没在真机上验证过"。**
所有工程化（CI、单测、审计、模拟器）都是在为那一次验证降低失败成本 —— 但它们替代不了那一次验证。
